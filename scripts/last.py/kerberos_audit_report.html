#01
GUARDS_DIR défini deux fois — le second écrase le premier
kerberos.py — Lignes 67 et 286
CRITIQUE ▼
GUARDS_DIR est défini deux fois dans kerberos.py. La première définition est correcte : elle utilise KERBEROS_ROOT pour pointer vers /guards. La seconde, ligne 286, pointe sur Path(__file__).parent soit la racine du projet. Toutes les fonctions qui utilisent GUARDS_DIR après la ligne 286 (onglet Guards, cortex, explainer…) travaillent sur le mauvais dossier.
État actuel — INCORRECT
L67 : GUARDS_DIR = KERBEROS_ROOT / "guards" # ✅ correct ... L285: MANIFEST_FILE = Path("guards_manifest.json") L286: GUARDS_DIR = Path(__file__).parent # ❌ écrase L67 — pointe sur /, pas /guards
▶ CORRECTION
# Supprimer complètement les lignes 285-286. # La définition L67 suffit. MANIFEST_FILE peut être : MANIFEST_FILE = GUARDS_DIR / "guards_manifest.json"
kerberos.py
#02
guards_manifest.json — 4 chemins différents selon le guard
guard_cortex.py, guard_auto_discovery.py, guard_auto_activate.py, guard_integrity_check.py
CRITIQUE ▼
Chaque guard cherche et crée le manifest à un endroit différent. Résultat : 4 fichiers manifest peuvent coexister avec des contenus différents. L'activation des guards est donc incohérente selon qui l'a lancé en dernier.
Chemins actuels — DIVERGENTS
guard_cortex.py : Path("guards_manifest.json") # relatif au CWD guard_auto_discovery : Path("guards_manifest.json") # relatif au CWD guard_auto_activate : GUARDS_DIR / "guards_manifest.json" # dans /guards guard_integrity_check: KERBEROS_ROOT / "guards_manifest.json" # à la racine
▶ CORRECTION
# Définir UNE constante partagée dans un module commun (ex: config.py) # ou dans kerberos.py et l'importer : MANIFEST_FILE = KERBEROS_ROOT / "guards_manifest.json" # → tous les guards utilisent la même source de vérité
guard_cortex.py guard_auto_discovery.py guard_auto_activate.py guard_integrity_check.py

#04
guard_yara.py — API yara-python incorrecte sur match.strings
guard_yara.py — L180
CRITIQUE ▼
L'accès aux chaînes détectées par YARA utilise des attributs s.plaintext et s.hex_data qui n'existent pas dans l'API yara-python. Le résultat : dès qu'une règle YARA trouve une correspondance, le guard plante avec AttributeError (silencieusement avalé).
Code actuel — CRASH
# guard_yara.py L180 "value": s.plaintext or s.hex_data # ❌ AttributeError — ces attributs n'existent pas
▶ CORRECTION (API yara-python correcte)
# Un StringMatch est un tuple : (offset, identifier, data) "value": s[2].decode('utf-8', errors='replace') if isinstance(s[2], bytes) else str(s[2]) # ou plus simple si on veut juste un label lisible : "value": repr(s[2])

#08
sync_main_metrics() jamais appelé dans kerberos.py
guard_ui_manager.py — API publique non connectée
IMPORTANT ▼
guard_ui_manager.py expose sync_main_metrics() avec la doc explicite "à appeler dans kerberos.py juste après l'import". Cet appel est absent. Résultat : _GUARD_METRICS de kerberos est un dict ordinaire et n'est jamais synchronisé avec le proxy du registry. Les VU-mètres lisent donc un dict fantôme.
Correction — dans kerberos.py, après le chargement du UI Manager
# Dans _init_guards() ou __init__, après l'import dynamique de guard_ui_manager : if hasattr(_ui_mod, 'sync_main_metrics'): _ui_mod.sync_main_metrics() # ← manquant
kerberos.py guard_ui_manager.py
#09
Double activation des guards — Cortex ET Auto-Activate font la même chose
guard_cortex.py + guard_auto_activate.py
IMPORTANT ▼
Les deux guards chargent le manifest et appellent start_guard() sur chaque guard listé. Si les deux sont actifs simultanément, chaque guard se retrouve chargé deux fois dans des threads séparés. Le flag anti-boucle de Cortex (CORTEX_FLAG_FILE) ne protège pas contre Auto-Activate qui a sa propre logique.
Rôles actuels — REDONDANTS
guard_cortex.py : charge manifest → active guards → flag anti-boucle guard_auto_activate.py: charge manifest → active guards → pas de déduplication croisée → Si les deux tournent : chaque guard x2
▶ CORRECTION — Choisir un seul orchestrateur
# Option A : Cortex = seul chef, Auto-Activate = déprécié # Option B : Auto-Activate délègue à Cortex : def start_guard(): from guards.guard_cortex import start_guard as cortex_start return cortex_start() # délégation propre
guard_cortex.py guard_auto_activate.py

Fallback actuel — TROP PERMISSIF

#13
guard_lymph_node.py — start_guard() retourne l'objet, pas le thread
guard_lymph_node.py — L220-226
IMPORTANT ▼
La convention Kerberos veut que start_guard() retourne le thread démarré (ou None pour les guards sans thread). LymphNode retourne l'objet LymphNodeFilter au lieu du thread, ce qui casse toute logique qui fait thread.is_alive() ou thread.join() sur le retour.
Code actuel
def start_guard(): node = LymphNodeFilter() thread = threading.Thread(target=node.monitor, daemon=True) thread.start() return node # ❌ retourne l'objet, pas le thread
▶ CORRECTION
return thread # ✅ convention respectée
guard_lymph_node.py
